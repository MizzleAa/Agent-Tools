# 프롬프트 설계와 다음에 추가할 것

관리 화면 **설정 · 프롬프트**가 다루는 것이 무엇이고 왜 이렇게 나눴는지, 그리고 다음에 무엇을 더하면 좋은지 정리한다.

## 1. 모델에게 가는 글은 네 종류

| 종류 | 언제 | 어디서 고치나 | 저장 |
|---|---|---|---|
| **시스템 프롬프트** | 실행 시작 (언어 규격은 도중에 붙음) | 용도 탭(역할·구성) + 공통 블록 | `config/agents/*.yaml`, `config/prompts.yaml` |
| **도구 설명** | 매 호출 (JSON 스키마와 함께) | 도구 설명 탭 | `config/prompts.yaml` (`tools`) |
| **루프 메시지** | 루프가 끼어들 때 (되돌려 보내기·한도·반복·실패) | 루프 메시지 탭 | `config/prompts.yaml` (`messages`) |
| **도구 결과 속 안내** | 셸 시간 초과, 설치 정책 차단 등 | (아직 코드. 4장 P0) | `agent/tools/shell.py` |

기본값은 `agent/prompt_defaults/`에 있고 고치지 않는다. 사용자가 바꾼 것만 `config/`에 저장된다. 그래서 '기본값으로'는 그 항목을 지우는 일이고, 프로그램이 업데이트되면 안 바꾼 항목은 새 기본값을 따른다.

## 2. 시스템 프롬프트 조립

```
[역할 프롬프트]           용도마다. 정체성·목표·일하는 순서·하지 말 것
[블록 1..n]               용도가 고른 순서대로
   work_rules             공통 작업 방식 (도구별 줄은 조건부)
   dev_standard           개발 규격 요약 (coder)
   intranet_status (자동) 등록된 사내 API·사이트·허용 주소
   environment            OS·셸·작업 폴더·날짜          ← 대화마다 바뀜
   lang_standard  (자동)  개발 언어를 알아채면 그 언어 규격 ← 실행 중에 붙음
```

- **순서 원칙: 안 바뀌는 것을 앞에, 바뀌는 것을 뒤에.**
  - llama-server는 직전 요청과 앞부분이 같으면 그 계산을 재사용한다.
  - 예전 순서(역할 → 환경 → 규칙 → 규격)는 두 번째 블록에 작업 폴더 경로가 있었다. 그래서 새 대화마다 그 뒤 약 2천 토큰을 다시 계산했다.
  - 지금 순서는 역할·규칙·규격이 대화끼리 같아 재사용된다.
  - 언어 규격은 실행 도중에 시스템 프롬프트를 바꾼다. 맨 뒤에 있어야 그 앞이 살아남는다.
- **조건 줄** `{{?도구}}`: 그 도구가 없는 용도에서는 그 줄을 뺀다.
  - 예전에는 general·researcher·intranet도 `run_command` 규칙 5줄을 받았다.
  - 없는 도구 얘기는 토큰 낭비이고, 소형 모델이 없는 도구를 부르게 만든다.
- **변수**: 내장(`cwd`, `today`, `tools` …) > 용도 변수 > 전역 변수.
  - 답변 언어처럼 여러 곳에 쓰는 값을 한 곳에서 바꾼다.

### 이번 변경으로 실제 프롬프트가 달라진 점 (QA 비교용)

| 용도 | 달라진 점 |
|---|---|
| coder | **문장은 하나도 안 바뀜.** 순서만: 역할 → 작업 방식 → 개발 규격 요약 → 실행 환경 (예전: 역할 → 실행 환경 → 작업 방식 → 규격) |
| general · researcher · intranet | `run_command`/`run_python` 규칙 4줄과 셸 문장이 빠짐 (그 도구가 없음). 순서는 위와 같은 원칙 |
| 루프 메시지 · 도구 설명 | 같은 문구 (저장소로 옮기기만 함) |

원래 순서로 돌리려면 용도 탭 '프롬프트 구성'에서 `environment`를 `work_rules` 위로 올린다.

## 3. 미리보기 점검 규칙 (lint)

저장 전에 '미리보기'가 잡아 주는 것:

| 수준 | 점검 |
|---|---|
| 경고 | 정의되지 않은 `{{변수}}` (오타, 한글 이름) |
| 경고 | 구성에 없는 블록 이름 |
| 경고 | 프롬프트가 **이 용도에 없는 도구**를 언급 (모델이 없는 도구를 부름) |
| 경고 | 사내 도구가 있는데 '사내 연결 현황' 블록이 없음 |
| 경고 | 명령 도구가 있는데 '실행 환경' 블록이 없음 (bash 명령을 쓰기 쉬움) |
| 경고 | '개발 규격 적용'이 켜졌는데 규격 요약·언어별 규격 블록이 없음 |
| 경고 | 시스템 프롬프트 + 도구 설명이 컨텍스트 예산의 35%를 넘음 |
| 경고 | 온도가 0에 가까움 (반복) |
| 참고 | 바뀌는 블록 뒤에 안 바뀌는 블록이 있음 (캐시) · 언어 규격이 맨 뒤가 아님 · 도구 9개 이상 |

토큰 수:
- 모델 서버가 켜져 있으면 `/tokenize`로 정확히 센다.
- 꺼져 있으면 한글 0.9 · 그 밖 0.3 토큰/글자로 어림한다.

현재 기본값(어림, 32k 모델 예산 28,672 기준):

| 용도 | 시스템 프롬프트 | 도구 설명 | 합계 | 예산 대비 |
|---|---|---|---|---|
| coder | 약 1,500 | 약 1,100 | 약 2,600 (+언어 규격 약 500) | 9% (11%) |
| general | 약 410 | 약 610 | 약 1,000 | 4% |
| researcher | 약 860 | 약 910 | 약 1,800 | 6% |
| intranet | 약 1,140 | 약 1,900 | 약 3,100 (+API 문서) | 11% |

16k 모델(예산 12,288)에서는 coder가 약 25%다. 개발 작업처럼 도구 결과가 긴 일에는 32k 모델이 낫다.

## 4. 다음에 추가할 것 (추천 순)

### P0 — 바로 하면 효과가 큰 것

1. **프롬프트 변경 ↔ eval 점수 연결**
   - 설정 화면에서 "이 용도로 eval 돌리기"를 실행하고, 저장 전후 점수표를 변경 기록에 붙인다.
   - 지금은 바꾼 게 좋아졌는지 눈으로만 본다. 소형 모델은 문장 하나로도 결과가 크게 바뀐다.
   - `eval/run_eval.py --profile`을 그대로 쓰고, 결과를 `data/eval/` + history id로 남기면 된다.
2. **남은 하드코딩 문구 외부화**
   - 셸 시간 초과 안내(`TIMEOUT_HINT`), 설치 정책 차단·환경 확인 안내(`ENV_HINT`), 사내 연결 현황 머리말, 승인 사유 문구.
   - 루프 메시지와 같은 방식(`messages`)으로 옮긴다.
3. **설정 잠금**
   - 비개발자가 실수로 프롬프트를 망가뜨리지 않게 '보기 전용' 기본 + 관리자 암호로 편집 모드를 둔다.
   - 지금은 토큰을 가진 같은 PC 브라우저면 누구나 고칠 수 있다.
4. **용도별 끝날 때 점검(gate) 규칙**
   - 지금 gate는 coder(개발 규격)만 있다. 같은 틀을 용도마다 설정에서 정의하게 한다.
   - 예) researcher "답 끝에 '출처' 목록이 있고, 그 주소가 이번 실행에서 실제 `fetch_url`로 읽은 주소인지"
   - 예) intranet "API 경로를 지어내지 않았는지(등록된 경로와 대조)"
   - 결정적으로 검사할 수 있는 규칙이 소형 모델에 가장 잘 듣는다.

### P1 — 품질을 한 단계 올리는 것

5. **모델별 프롬프트**
   - 블록에 `{{?ctx_32k}}` 같은 조건 변수, 또는 "16k 모델에서는 이 블록 대신 짧은 판"을 둔다.
   - 같은 coder라도 9B와 35B-A3B는 필요한 설명 양이 다르다.
6. **예시(few-shot) 관리**
   - 잘 끝난 실행 기록에서 "좋은 예시로 저장"을 누르면 요청 → 도구 순서 → 보고 요약을 그 용도의 `examples` 블록에 넣는다.
   - 소형 모델은 규칙 열 줄보다 예시 하나를 더 잘 따른다.
7. **용도 가져오기/내보내기**
   - 용도 하나(프로필 + 쓰는 블록 + 변수 + 도구 설명)를 파일 하나로 묶는다. 폐쇄망 PC로 옮기거나 팀원과 나눌 때 쓴다.
8. **답변 형식 템플릿 + 검사**
   - 보고서·표·JSON 같은 출력 형식을 용도별로 정하고, 형식이 깨지면 4번 gate로 한 번 되돌려 보낸다.
9. **용도 추천** (자동 선택 아님)
   - 입력한 요청을 보고 "이 요청은 researcher가 맞아 보입니다"를 입력창에 표시만 한다.
   - 별도 라우터 모델 없이 용도 설명 + 키워드로 충분하다.

### P2 — 규모가 커지면

10. **블록 우선순위로 예산 자동 맞추기**
    - 컨텍스트가 작거나 대화가 길어지면 '선택' 블록부터 뺀다. 지금은 오래된 도구 결과만 줄인다.
11. **대화 요약 블록**
    - 오래된 턴을 지울 때 버리지 않고 "지금까지 한 일" 요약을 시스템 프롬프트 끝에 둔다.
    - 긴 작업에서 앞에서 정한 것을 잊는 문제를 줄인다.
12. **프롬프트 인젝션 회귀 과제**
    - 악성 지시가 든 웹 페이지·파일·API 응답을 eval 과제로 만들고, 프롬프트를 바꿀 때마다 같이 돌린다.
13. **A/B 비교 실행**
    - 같은 요청을 두 프롬프트 판으로 차례로 실행해 결과를 나란히 본다 (GPU 하나라 순차).
14. **계획서에 남은 용도**
    - 문서 Q&A(`librarian`, RAG)와 무인 반복 실행(`automation`, 스케줄)을 이 설정 틀 위에 용도로 추가한다.

## 5. 워크플로 (구현됨)

여러 에이전트를 노드처럼 잇는 방식이다. Claude Code 의 서브에이전트·워크플로와 같은 생각이다.

| | 이 프로젝트의 선택 | 이유 |
|---|---|---|
| 순서 | 프로그램이 정함 (사람이 만든 노드 목록) | 소형 모델은 일을 나누고 합치는 계획이 약하다 |
| 컨텍스트 | 노드마다 새로 시작, 앞 노드는 **최종 답만** 넘김 | 긴 도구 결과가 뒤 노드 컨텍스트를 차지하지 않는다 |
| 실행 | 하나씩 차례로 | GPU 하나·슬롯 하나. 동시에 돌리면 번갈아 처리하며 앞부분 캐시가 깨져 오히려 느려진다 |
| 파일 | 같은 대화 폴더를 같이 씀 | 차례로 돌므로 충돌이 없고, 앞 노드가 만든 파일을 뒤 노드가 읽는다 |
| 실패 | 기다리는 노드가 실패하면 건너뜀, 기본은 멈춤 → '멈춘 노드부터 계속' | 성공한 노드를 다시 돌리지 않아 시간이 절약된다 |

노드 지시문을 쓰는 요령:
- 한 노드에는 한 가지 일만 시킨다.
- 검토 노드는 쓰기 도구가 없는 용도(reviewer)로 돌린다. 그러면 결과를 고치지 않고 확인만 한다.
- 뒤 노드에는 원래 요구(`{{input}}`)와 앞 노드 결과를 **둘 다** 준다. 앞 노드의 보고만 주면 잘못된 보고도 그대로 믿는다.

다음 단계 후보:
- 노드 출력 형식 검사 (예: 검토 노드 답에 표가 있는지)
- 조건 분기 (예: 검토 결과가 '문제 없음'이면 고치기 건너뛰기)
- 반복 (검토 ↔ 고치기를 최대 N번)
- `-np 2` 슬롯을 쓴 진짜 병렬 (서로 기다리지 않는 노드가 많을 때만)

## 6. 소형 모델(8~35B)용 프롬프트 작성 요령

- 한 줄에 규칙 하나, 명령형("~한다")으로 짧게 쓴다. 부정형만 쓰지 말고 대신 할 일을 같이 쓴다.
- 일하는 순서를 번호로 쓴다 (확인 → 실행 → 검증 → 보고).
- 같은 규칙을 여러 블록에 되풀이하지 않는다. 우선순위가 흐려지고 토큰만 든다.
- 도구 이름을 프롬프트에 쓸 때는 그 용도에 그 도구가 있는지 확인한다. 미리보기가 찾아 준다.
- 루프 메시지는 "무엇을 하라"를 한 가지만 쓴다. 경고만 하고 대안이 없으면 같은 실수를 되풀이한다.
- 바꾼 뒤에는 같은 요청으로 전후를 비교한다 (eval). 나빠지면 '변경 기록'에서 되돌린다.
